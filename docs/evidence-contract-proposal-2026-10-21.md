# 実行記録の写し（3 タブ）— PIATEC からの形式案

対象：NIKUSHO 閲覧用の写し（v1）に追加していただく 3 タブ（判定ルール 2026-10-21 §6-5・§7「発注者側 CODE・Codex」分担）
状態：**PIATEC の提案（未確定）**。列名は判定ルール §6-5 の最小列のとおりです。タブ名・値の一覧・任意列は、ご確認のうえ確定してください。
PIATEC は読み取りのみ行います。送信処理の再実行、元シートや本番設定の変更は行いません。

## 0. 共通

- 置き場所：「NIKUSHO 閲覧用の写し（v1）」の中に新しいタブとして追加（閲覧キーの範囲は 2 ファイルのまま）。
- タブがまだ無い間：画面は現在どおり「未確認」「3 経路判定未接続」「最終稼働時刻のみ確認／全件判定未接続」と表示します。
- 時刻：`2026-10-20T12:04:00+07:00`（オフセット付き ISO）、または現在の写しと同じ `yyyy/MM/dd H:mm:ss`（Asia/Bangkok）。
- 1 行目は列名。列の順番は自由。下記以外の列があるとそのタブは使用しません（安全側）。
- 含めないもの：内部パス、鍵、スタッフの生 ID・LINE ID、顧客の原文、URL。含まれていた場合、そのタブは使用しません。
- 任意：`meta` タブに各タブの行（`tab` = タブ名、`status` = ok / stale / error）を追加できます。`ok` 以外のときは使用しません。
- 値が下記の一覧に無い場合・行が矛盾する場合は、成功にせず「結果不明」と表示します。

## 1. タブ `定時読取`（12・17・22 時、1 便 1 行）

| 列 | 内容 | 例 |
|---|---|---|
| `run_id` | 便の一意 ID（匿名でよい） | `20261020-1200` |
| `scheduled_at` | 予定時刻 | `2026-10-20T12:00:00+07:00` |
| `started_at` | 起動時刻（無ければ空欄） | `2026-10-20T12:00:31+07:00` |
| `finished_at` | 終了時刻（無ければ空欄） | `2026-10-20T12:04:10+07:00` |
| `source_complete` | 対象時間帯の記録を最後まで取得できたか | `TRUE` / `FALSE` |
| `status` | 下表のいずれか | `ok` |
| `reason` | 停止・失敗時の短い理由（個人情報なし） | `exit_code=2` |
| `read_count`（任意） | 読んだ件数 | `57` |

`status` の値（案）：

| 値 | 意味（発注者側で判定） | 画面 |
|---|---|---|
| `ok` | §3 の読取完了条件（`mode=read`・`result=ok`・`exit_code=0`、同便の読取心拍 `ok`・`manifest=ok`・件数あり）をすべて満たす | 読取完了（終了が締切後なら 遅れて読取完了） |
| `fail` / `stopped` / `safety_stop` | 明示的な失敗・非 0 終了・安全停止 | 停止（`reason` を表示） |
| `started` | 起動行はあるが終了行が無い | 締切前は 実行中、締切後は 結果不明 |
| `not_started` | 起動行が無い | `source_complete=TRUE` かつ締切後のみ 未実行。`FALSE` なら 未確認 |

10/5 23:36 より前の便は旧ルールのため、行があっても判定しません。行が無い便は「未確認（記録なし）」で、未実行とはしません。

## 2. タブ `5分巡回`（1 回 1 行）

| 列 | 内容 | 例 |
|---|---|---|
| `at` | 実行時刻 | `2026-10-20T12:05:00+07:00` |
| `host` | 実行した PC（本番機の名前） | `snowmaru` |
| `send` | `heartbeat.jsonl` の `send` | `TRUE` |
| `issues` | 内部問題の件数 | `0` |
| `audit_issues` | 監査問題の件数 | `0` |
| `google_beat` | Google 心拍の成否 | `ok` / `fail` |
| `owner`（任意・**お願い**） | `ownership.json` の MEAT・IN 担当 | `new` |

画面：本番機の最新行が 15 分以内で `send=TRUE`・`issues=0`・`audit_issues=0`・`google_beat=ok`・`owner=new` のときだけ「動作確認（その回のみ）」。`owner` が無い／`new` 以外は「担当未確認」、問題があれば「要確認」、15 分超は「遅延／要確認」、20 分超は「停止検知」。待機機・他の PC の行は使いません。返信成功率・全件成功率は、案件台帳がつながるまで「未集計」です。

## 3. タブ `日次配送`（営業日 × 経路で 1 行、1 営業日 3 行）

| 列 | 内容 | 例 |
|---|---|---|
| `business_date` | 営業日 D（翌日 00:35 頃に送るもの） | `2026-10-20` |
| `route` | `staff_all_line` / `owner_line` / `owner_email` | `owner_email` |
| `attempted_at` | 送信口の受付時刻 | `2026-10-21T00:32:00+07:00` |
| `status` | `sent` / `attempted` / `unknown` / `blocked` | `sent` |
| `body_sha256` | 本文 SHA-256（64 桁 16 進） | `9f86d0…` |
| `body_changed_after_attempt` | 試行後に本文が変わったか | `FALSE` |

画面：3 経路すべて `sent`・同じ SHA・本文変更なしで「3 経路受付記録あり」（最後の受付が 01:35 より後なら「遅れて受付」）。どれか 1 つでも `attempted`／`unknown`・SHA 不一致・本文変更あり・記録の無い経路があれば「結果不明」（再送しません）。`blocked` は「停止」。経路ごとの状態も表示します。`sent` は送信口の受付であり、受信・既読の意味ではないと画面に明記します。00:00 以降 00:35 前の受付（例 00:32）は正常として扱います。

## 4. ご確認いただきたいこと

1. タブ名 `定時読取` / `5分巡回` / `日次配送` でよいか。
2. `status`・`route` の値の一覧（上記）でよいか。別の値を使う場合は一覧をください。
3. `5分巡回` に任意列 `owner`（`ownership.json` の担当）を追加できるか。無い場合、画面は「担当未確認」のままです。
4. `定時読取` に任意列 `read_count` を追加できるか（無くても判定はできます）。
5. 追加前に、匿名のサンプル数行（10/20 分など）を写しに入れていただければ、画面と原本の突合結果（時刻・状態・理由）をお返しします。
